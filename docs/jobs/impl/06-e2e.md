# P6: journey tests for two fictional people (end to end)

Part of [the Jobs design](../design.md): read §2 (every journey: 2.2–2.9 and 2.3a), §13, §14, §19 (testing and acceptance)
and §22 row P6 first. Rules for every implementer: [README.md](README.md). P1–P5 built everything these tests drive; P6 adds
no feature. It adds the journey tests, the fixtures they need, and fixes for the real bugs the journeys find (each with a
test).

## 1. Scope
One journey file per fictional person, both running the same script with their own data:

| File | Person | Shape |
|---|---|---|
| `test/jobs/e2e/berlin-analyst.test.ts` | Ada Example (`test/fixtures/jobs/people/berlin-analyst`) | on-site/hybrid in Berlin, EUR per year (top of range), German titles, `onsite-city` preset |
| `test/jobs/e2e/us-nurse.test.ts` | Riley Example (`test/fixtures/jobs/people/us-nurse`) | remote from Texas/Arizona, USD per hour (bottom of range), per-diem, `healthcare-us` preset |

The script (`test/jobs/e2e/journey.ts`) is a list of `node:test` steps that share one world per file: a fresh temp
`CREWDECK_HOME` (set before any Crewdeck module loads), a temp vault, one local fixture site, the real shell server
(`createShell` on a random port, Jobs on, the agent token from `ensureToken`) and the real CLI (`node src/cli.ts …`
spawned with the temp home, stdin piped, so never a TTY). Steps, in order:

1. **Setup (§2.2).** `crewdeck init`'s effect without SilverBullet (config.yaml with the vault, the token, the vault from
   `vault-template`), `jobs init --preset <p> --no-providers`, then the interview's writes through validated commands only:
   `me set` (identity, standard answers, education, resume, sections, facts, skills), `pref set … --because-file` for every
   search field, `remember` for the person's memory, `jobs/sources.md` edited by hand (as the setup skill does), `jobs check`
   clean (exit 0, no errors) and `jobs rules`.
2. **No session yet (§2.9).** `/api/jobs/state` says not connected and the rendered banner says "No Claude session is
   working Jobs".
3. **Sources (§2.4).** A fixture provider tree is installed through the real `installProviders` (download through
   netguard from a local "raw" server, per-file sha256, sealed folder) and re-verified with `verifyProviders`. The page's
   **Refresh sources** POST starts the server's scheduler, whose run is the real `runSources` (the sandboxed child, the
   checks, the tracker, the prefilter, descriptions for the best roles through netguard, the prefilter again). Each
   person's feeds hold roles the rules must drop for them: titles, workplace kinds they excluded, places elsewhere,
   pay below the floor in another currency or period, an excluded company, travel found only on the posting page.
4. **Find (§2.4).** The page's **Find N jobs** → a `find` request → claim → `request show` (count, daily picks) →
   `candidates --budget 40 --batch 3 --need 2 --start`, a scripted judge (no model) through `judge --results-file`, again
   until the run is done (progress lines on the request); `pick`: one role per company, the daily count, `picked_on` is
   the person's local day; a second `pick` is idempotent; the request closes and "new roles since" counts from it.
5. **Paste a link (§2.3).** Page `addLink` → a `link` request on lane `jobs` → the bridge's claim with the token (proof
   checked; the claim carries payload keys, never the URL) → `crewdeck jobs request show <id>` → `jobs link --request`
   (see decision 1) → the role is picked → `crewdeck progress` and `crewdeck request done --result-file`.
6. **Prepare (§2.3 step 4).** The form read headlessly through the guarded browser; `draft --brief` (profile answers
   approved with `profile:` sources, memory answers with `m-N`); `draft --answers` with a fixture "model output"; one
   claim names a term its fact doesn't contain, so the citation check turns it into a first-time question; Apply is
   refused until it is answered; the page's answer POST is remembered in `jobs/memory.md` (the user's words, a key) and
   fills the same question on a second role's form (a Find pick) automatically; `resume --variant-file` renders the PDF
   (real Chromium, JS and network off) and the page serves it.
7. **Apply (§2.3a).** Page `approve` → `apply` request → claim → progress → the form "changes" (a new required question, a
   password field and a CAPTCHA appear) → `fill-plan --request` with the fields a test-only driver read → the driver
   (Playwright through the guarded browser, test code only) applies exactly the plan: every planned field is set,
   sensitive and unanswered fields stay empty, password and CAPTCHA untouched, no file attached, the submit button never
   clicked and the form never submitted (page counters and the server's POST count) → the new question closes the request
   as `needs you: …` → answered on the page → Crewdeck queues `apply` again → second pass fills it → "your turn" with the
   progress lines in the apply panel (the real view model rendered with the real screen) → page **Mark applied**: status
   applied, company cooldown, the journal line in the vault, open requests (an `improve` asked meanwhile) closed; pasting
   the same link again comes back with the applied/cooldown warnings; a link at a company with a role in progress comes
   back with that warning, and only the page's "Add it anyway" (`force` in the request) picks it.
8. **Preference change and Not interested (§2.5, §2.6).** `pref set workplace … --because-file` (and the Berlin person's
   `places.remote_from`) → dated Changes lines in the user's words → `refilter --days 14` brings back exactly the role the
   new preference allows. Not interested on the page with a reason and title words → skipped, an `avoid` item, the words
   in `search.md` (with a Changes line), the reason in `judge-brief`; the next Refresh sources drops a new posting with
   those words.
9. **Risky features (§2.8, §12).** A LinkedIn link is refused by the page and by `link --url-file` while off; an Easy
   Apply plan comes back as copy mode while off; `jobs features … on` refuses without a TTY; an agent token can't call the
   page's toggle; the page toggle switches it on (config.yaml changes, the CLI sees it: a LinkedIn link queues, an Easy
   Apply plan fills and counts against the cap) and off again.
10. **A broken note (§2.9).** The user breaks `jobs/search.md` in Notes → `jobs check` names the field path and says the
    last valid version is used; the page's banner names the path; `jobs rules` still uses the last valid values; fixing
    the note clears it.
11. **Captured outputs.** Each file prints one `e2e <person>:` diagnostic line (JSON) with the role counts at each stage
    and the final application record; §Done summarises them.

Not in P6: the security review (P7), screenshots and README (P8), a live Claude session (the owner's acceptance run).

## 3. Decisions
1. **Network steps run in-process with netguard's test allowance; the CLI never gets one.** P2b decision 2 keeps
   `testHosts` a library option that no flag or variable reaches, so a spawned `jobs link --request` can't read a page on a
   fixture host (the journey checks that it refuses it). The journey then runs the same command body in-process: the
   payload read from the running server by id with the token (`showRequest`, the CLI's own call), then `link(ctx, payload,
   { net })`. Headless form reading (`readForm`), the provider install and the description fetch do the same. Everything
   that touches no network (`request show`, `progress`, `request done`, `draft`, `resume`, `fill-plan`, `learn`, `pick`,
   `judge`, `candidates`, `refilter`, `pref`, `me`, `remember`, `check`, `rules`, `judge-brief`, `features`) is the real
   spawned CLI.
2. **Sourcing goes through the page and the server's scheduler.** Refresh sources (a page POST) starts the scheduler; its
   `run` (a `JobsApiOptions.sources` test option, as in P5's tests) calls the real `runSources` in-process with the fixture
   manifest instead of spawning `jobs source`, because the CLI checks the pinned career-ops manifest only (no seam either).
   The sandboxed child, the per-job checks and both prefilter passes are the real ones.
3. **Fixture providers validate as real entries.** `jobs/sources.md` lists watchlist companies by `careers_url` (on
   `careers.example.test`) plus a `feed` address on the local site; such entries need no provider id, so the note
   validates against the real manifest, and the fixture manifest's detector claims them as career-ops routes careers pages.
4. **`crewdeck init` without SilverBullet.** The journey writes what `init` writes (config.yaml, the token, the vault from
   `vault-template`) and skips the SilverBullet download; `jobs init` is the real command.
5. **One browser per file for the driver.** Headless form reading launches its own guarded browser per call and the PDF
   render its own (both are the real paths and must stay separate: the PDF has the network off). The test-only driver
   opens one guarded browser for the file and reuses its page for both Apply passes.
6. **Both needs-you paths.** The Berlin person's Claude records the new question with `jobs learn` before closing the
   request (the page answers that field); the nurse's Claude only closes with `needs you: <question>` (the page answers the
   request, which records the question). Both end with Crewdeck queuing `apply` again.
7. **The daily count binds.** Both people answer the interview with `schedule.daily_picks: 2`, so Find stops early and
   `pick` leaves eligible roles on the bench.
8. **Driver rules.** The driver fills only items whose action is `fill`, `select` or `choose`, finds each field by the
   selector it recorded while reading (never by guessing), never touches password, CAPTCHA, file or button fields, and
   never clicks a button. It lives in `test/` only; `src/jobs` still has no click/fill/type code (web-guard test).

## 4. Runtime
Both files run in parallel under `npm test`. The slow parts are the spawned CLI (≈ 60 calls per person), four Chromium
launches per file (two form reads, the PDF, the driver) and two sandbox runs. Target: under 3 minutes for the two files;
measured ≈ 15 s for both (Node 25.9, Brave headless), and the whole suite ≈ 18 s.

## Done
Built as planned in §1–§3: 16 steps per person, 32 journey tests, all green; the whole suite is 375 tests (1 skipped
without a career-ops checkout), green with the leak scan; `npm audit --omit=dev --audit-level=high` clean.

**Bugs the journeys found (fixed in `src/`, each with a test):**
1. **A preset never applied after `crewdeck init`.** `crewdeck init` copies `vault-template`, which has the jobs notes since
   P1, so `jobs init --preset` always found `jobs/search.md` and `jobs/sources.md` "already there" and skipped the preset
   for every new user (P4's tests removed those notes before `init`, which no real install does). `seedNotes` now treats a
   note that is still byte-for-byte the template as not written yet and replaces it with the preset (atomically, checked
   again right before the swap, 0600); the preset applies to both notes or to neither, so a user's edit to either keeps
   both. Test: `setup.test.ts` "jobs init --preset right after crewdeck init".
2. **A Yes/No "needs you" answered on the page was remembered for one company only.** When Claude closes an apply with
   `needs you: <question>` without recording it, the page's answer records the question with no options, so it was a
   "written" question and the user's "Yes" was kept for that company: the same question on the next company's form asked
   again (design §2.3a step 4, §8). `learnField` now treats a question answered Yes or No without recorded options as a
   Yes/No choice about the user (remembered for every company). Test: `kb.test.ts` "learn: a Yes/No answer …"; the nurse
   journey checks the scope.
3. **The last-valid fallback's time had no zone.** `jobs check` said "using its last valid version (2026-11-18 23:20)" in
   UTC to a user in another zone; it now says "… 23:20 UTC)". Test: `notes.test.ts` last valid.
